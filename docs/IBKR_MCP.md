# IBKR hosted MCP — M3 market data

M²D can establish its own connection to IBKR's official hosted MCP server at `https://api.ibkr.com/v1/api/mcp-public`. This is a user-authorized exception to the original broker-connection exclusion, limited to market data. It does not use the authorization of a ChatGPT/Codex plugin, require TWS/IB Gateway, synchronize accounts, or create trading instructions.

## Connect

1. Keep the working market provider selected while connecting. Set `PUBLIC_APP_URL` in the ignored root `.env` to the exact browser origin, including its port. Default: `http://127.0.0.1:3000`. A remotely hosted installation must use HTTPS. This is an origin, without a path.
2. Recreate the app: `docker compose up --build --detach --wait --wait-timeout 180`.
3. Open **Market → Interactive Brokers → Connect IBKR**. Complete authentication and consent on IBKR's website. Return to M²D through `/api/ibkr/callback`.
4. Choose **IBKR** in the **Price provider** selector on Portfolio or Market. The selection saves automatically; no container restart is needed. IBKR can also be selected separately for listing descriptions, which may be abbreviated and do not include logos.

No new API key or OpenAI call is required. IBKR data entitlements and applicable subscriptions determine availability. M²D cannot verify account-wide coverage until the separately authorized application makes a market request. Read-only navigation and Agent tools use stored evidence; external market requests remain explicit user actions.

## Authorization boundary

- The official MCP SDK handles discovery, dynamic client registration, PKCE, token exchange and refresh. OAuth always requests **only `mcp.read`**, explicitly overriding the SDK's broader advertised-scope default. Tokens granting additional scopes are rejected. IBKR's read scope itself can cover account data; the application tool allowlist excludes it.
- The only permitted MCP tools are `search_contracts`, `get_price_snapshot`, `get_price_history`, `get_option_parameters` and `get_option_data`. Discovery never exposes other tools to Agent, and runtime checks also reject account, position, balance, order, instruction, alert and watchlist calls. There is no arbitrary MCP endpoint, tool name, resource reader, sampling, elicitation or shell interface.
- The endpoint and authorization issuer are pinned to `https://api.ibkr.com`; redirects and unexpected authentication endpoints are rejected. A short-lived browser HttpOnly/SameSite cookie binds the callback to the browser that started it. Backend state expires after ten minutes, is consumed before exchange, and must match the authorization-response issuer. OAuth codes and tokens are not returned by public status endpoints or logged by API request logging.
- OAuth client registration and tokens are persisted in the API-only `ibkr_credentials` Docker volume, at `/app/data/credentials/ibkr.json`, with restrictive file modes and atomic replacement. The file is a secret, like `.env`: do not commit it, share it, mount it into the web service, or include it in an unprotected backup. Native development uses ignored repository `data/credentials/ibkr.json`; `IBKR_CREDENTIAL_PATH` can override the backend path. This is separate from portfolio/database backups. `docker compose down` preserves the volume; do not use `--volumes` on the real app.
- Expiring tokens refresh on the next requested connection, without a background polling task. Expired/revoked grants require reconnecting. Disconnect removes local tokens and pending authorization; it does not revoke IBKR's server-side consent. Revoke that separately in **Client Portal → Settings → Manage Third-Party Consents**.

Listing names and logos can separately use `LISTING_PROVIDER=massive` with the existing Massive key while IBKR remains the price provider. See [listing metadata setup](M3_MARKET.md#listing-names-and-logos). The initial IBKR MCP adapter does not provide company logos.

## Supported evidence and limits

- Initial coverage is USD US-listed stocks/ETFs and standard 100-share equity options. FX and currency trading are not enabled. Missing non-USD conversion evidence leaves NAV incomplete.
- Resolve an exact symbol to one US primary listing and contract identifier. An explicit conflicting exchange or an ambiguous listing is rejected. IBKR uses `STK` for both stocks and ETFs; M²D preserves the recorded class rather than inferring one from a description. The original ledger key remains unchanged; provider listing metadata is stored with the quote.
- Option identity requires the exact underlying, expiry, strike, right, unadjusted trading class and matching returned description. Expiration identifiers are taken verbatim from IBKR. Adjusted classes and nonstandard multipliers/deliverables are rejected. The MCP response does not expose a complete deliverable schedule: the standard root-class convention and the explicitly recorded standard 100-share terms are the supported boundary, not independent verification of corporate actions.
- Snapshots use the provider's last-trade timestamp. A bid/ask pair without its own matching source timestamp is omitted; prior close never substitutes silently for a current mark. Frozen/unspecified status and unknown entitlement delay remain `UNKNOWN`; explicit delayed status is labeled `DELAYED`. No real-time license claim is inferred from the tool's name. All M3 evidence remains `WATCH_ONLY`.
- Historical bars request up to 100 hourly `Last` bars, exclude unfinished intervals, validate matching arrays/OHLC ranges, and retain their interval end as as-of. `expires` is not a trade timestamp. The hosted response does not establish adjustment policy, so these bars explicitly carry `adjustment: UNKNOWN` and the UI shows that limitation.
- The option-chain tool returns structure only. A chain refresh requests a bounded range around a timestamped spot price, then snapshots up to three nearby strikes, both call and put (at most six contracts total). This is a sample, not the full chain. Greeks, IV, volume and open interest stay null in this initial adapter. Portfolio options use exact individual-contract refreshes, independently of the sample.
- Each refresh allows at most twelve tool calls and stops dispatching after ninety seconds; an already-running HTTP request has a twenty-second timeout. MCP HTTP dispatches share a PostgreSQL-backed one-second gate; this is a conservative application ceiling, not a claim about IBKR's published allowance. The existing global refresh lock and request-key idempotency still apply. Provider-wide authorization, entitlement, quota and transport failures stop the batch and impose a durable cooldown. There is no automatic tool retry or entitlement upgrade.
- Raw tool evidence is stored with normalized records, including separate source, received and available timestamps. Missing/invalid observations never overwrite last-good evidence or zero a holding. Financial state remains self-reported and requires the existing preview/confirmation flow.

## Persistence and verification

Additive migration `0011` admits `ibkr` in market evidence and provider rate-limit constraints. No account, holding, cash or event schema changes are needed. The Drizzle snapshot accompanies the migration. The ERD was regenerated and checked; constraint-only changes leave its diagram unchanged. Quote/provider contracts are additive; historical bars additionally accept `UNKNOWN` adjustment. HTTP endpoints remain version 1.

The Market connection uses backend `/api/v1/market/ibkr/{status,connect,callback,disconnect}` endpoints. The browser starts authorization through `/api/ibkr/connect`, which sets the browser-binding cookie, and returns through `/api/ibkr/callback`, which forwards the exchange privately and removes sensitive query parameters by redirecting to Market. The generic web API proxy exposes only connection status and disconnect.

Offline tests use mocked MCP/OAuth transports and do not require an IBKR account, keys, paid inference or real data subscriptions. Production authorization must be completed by the account owner; a separately connected desktop plugin does not establish application authorization.
